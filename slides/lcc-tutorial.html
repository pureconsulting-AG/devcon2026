Tutorial

lcc
local code cli

Eine Coding-CLI, die nur mit deinem lokalen Ollama-Server arbeitet – Schritt für Schritt, ein Fall pro Folie.

qwen3.5:9bbge-m3 kein Cloud-Modellkeine Telemetrie

Blättern mit den Buttons unten oder ← / → · F für Vollbild

Überblick

Was lcc kann

Fragen

lcc ask – Antworten ohne Werkzeuge, auch zu Dateien per Pipe.

Code

lcc run – liest, sucht, ändert Dateien. Mit Diff & Rückfrage.

Interaktiv

lcc – REPL mit Verlauf und Slash-Befehlen.

RAG

Eigene Doku durchsuchen und mit Quellen [n] zitieren.

Skills

Kleine Anleitungen, die lcc nur bei Bedarf lädt.

Kleine Modelle

Plan → Schritte → Prüfen → Reparieren statt langer Prompts.

So ist das Tutorial aufgebaut: je Lektion eine Einstiegsfolie, dann ein Fall pro Folie – mit Ziel, Befehl, Ergebnis und dem Wichtigsten zum Merken.

Lektion 1

Fragen stellen

lcc ask beantwortet Fragen – ohne Werkzeuge, ohne etwas zu ändern.

Das lernst du

  1. eine einfache Frage stellen
  2. eine Datei erklären lassen
  3. eine Fehlermeldung erklären lassen
Lektion 1 · Fragen stellen Fall 1 / 3

Eine Frage stellen

Ziel: Eine schnelle Antwort, ganz ohne Projekt-Kontext.

Du tippst
lcc ask "Unterschied zwischen Liste und Tupel in Python? Kurz."
Du siehst
⠹ denkt nach … 3s
Eine Liste ist veränderbar, ein Tupel nicht. …
Merke: ask nutzt keine Werkzeuge und ändert nie etwas. Der Spinner zeigt, dass das Modell arbeitet.
Lektion 1 · Fragen stellen Fall 2 / 3

Eine Datei erklären lassen

Ziel: Eine Datei als Kontext mitgeben – per Pipe.

Du tippst
cat bestellung.py | lcc ask "Erkläre diese Datei in drei Sätzen."
Du siehst
Die Datei berechnet Versandkosten …
lies_formular übernimmt die Felder …
bestellung_bearbeiten verbindet beides …
Merke: Alles, was über stdin kommt, hängt lcc an die Frage an.
Lektion 1 · Fragen stellen Fall 3 / 3

Eine Fehlermeldung erklären lassen

Ziel: Die Ausgabe eines Programms direkt weitergeben.

Du tippst

Du siehst
Der TypeError entsteht, weil gewicht_kg ein String ist
("2.5") und mit einer Zahl multipliziert wird. …
Probier auch: 2>&1 schickt auch die Fehlerausgabe in die Pipe. Beheben lassen wir den Fehler in Lektion 4.

Lektion 3

Code ändern – und zurücknehmen

lcc ändert Dateien nur mit deinem Okay. Jede Änderung lässt sich zurücknehmen.

Das lernst du

  1. eine Funktion hinzufügen lassen
  2. die Änderung prüfen und zurücknehmen
  3. Shell-Befehle und die Allowlist
  4. ohne Rückfragen arbeiten
Lektion 3 · Code ändern – und zurücknehmen Fall 1 / 4

Eine Funktion hinzufügen

Ziel: lcc schlägt eine Änderung vor – du entscheidest.

Du tippst
lcc run --no-small "Füge in utils.py eine Funktion ist_gerade(n) hinzu."
Du siehst
Änderung an utils.py:
--- a/utils.py
+++ b/utils.py
+def ist_gerade(n: int) -> bool:
+    return n % 2 == 0
[j]a / [n]ein / [i]mmer für diese Session:
Merke: j erlaubt, n lehnt ab (das Modell erfährt es), i erlaubt alle weiteren Änderungen in diesem Lauf.
Lektion 3 · Code ändern – und zurücknehmen Fall 2 / 4

Prüfen und zurücknehmen

Ziel: Sehen, was geändert wurde – und es rückgängig machen.

Du tippst
git diff utils.py
lcc undo
git diff utils.py
Du siehst
+def ist_gerade(n: int) -> bool:
+    return n % 2 == 0
Zurückgenommen: utils.py wiederhergestellt.
(keine Änderungen mehr)
Merke: lcc undo geht mehrfach hintereinander und löscht auch Dateien, die lcc neu angelegt hat. Backups liegen in .lcc/undo/.
Lektion 3 · Code ändern – und zurücknehmen Fall 3 / 4

Shell-Befehle und Allowlist

Ziel: Verstehen, wann lcc vor einem Befehl fragt.

Du tippst
lcc run --no-small "Führe main.py aus und sag mir das Ergebnis."
Du siehst
→ run_shell(command='python main.py')
Shell-Befehl ausführen: python main.py
[j]a / [n]ein / [i]mmer für diese Session:
Merke: Ohne Rückfrage erlaubt: ls, cat, rg, grep, git status, git diff, pytest, python -m pytest, python -m py_compile. Alles andere wird bestätigt.
Lektion 3 · Code ändern – und zurücknehmen Fall 4 / 4

Ohne Rückfragen arbeiten

Ziel: Änderungen direkt schreiben lassen – du prüfst danach mit git diff.

Du tippst
lcc run --yes "Füge in utils.py eine Funktion ist_gerade(n) hinzu."
git diff
Du siehst
→ edit_file(path='utils.py', …)
  ↳ 1 Zeilen
Funktion ist_gerade hinzugefügt.
Merke: --yes gilt nur für Dateien. Shell-Befehle außerhalb der Allowlist bleiben bestätigungspflichtig – ohne Terminal werden sie abgelehnt.

Lektion 4

Kleinmodell-Modus

Kleine Modelle scheitern an langen Aufgaben. lcc hilft mit Struktur: Plan → Schritte → Prüfen → Reparieren.

Das lernst du

  1. einen Plan ansehen und bestätigen
  2. Schritte und Prüfungen verfolgen
  3. einen Plan bearbeiten
  4. verstehen, was bei roten Prüfungen passiert
Lektion 4 · Kleinmodell-Modus Fall 1 / 4

Den Plan ansehen

Ziel: Den Fehler aus Lektion 1 beheben – lcc plant zuerst.

Du tippst
cat traceback.txt
lcc run "Beim Start von main.py kommt der Fehler aus traceback.txt. Finde die Ursache in bestellung.py und behebe sie."
Du siehst
⚙ Skill: fehler-analysieren
Kleinmodell-Modus (qwen3.5:9b, 9.7B)
Plan:
1. [explore] bestellung.py lesen (bestellung.py)
2. [edit] Gewicht in lies_formular in float umwandeln
[Enter] ausführen / [e] bearbeiten / [n] abbrechen:
Merke: Automatisch aktiv bei Modellen bis 14 Mrd. Parameter. Phasen: explore = lesen, edit = ändern, verify = prüfen. Der genaue Plan variiert.
Lektion 4 · Kleinmodell-Modus Fall 2 / 4

Schritte und Prüfungen

Ziel: Mit Enter den Plan ausführen und zusehen.

Du tippst
[Enter]
Du siehst
▶ Schritt 1/2 [explore]: bestellung.py lesen
→ read_file(path='bestellung.py')
▶ Schritt 2/2 [edit]: Gewicht in float umwandeln
→ edit_file(path='bestellung.py', …)
✓ Check bestanden: python -m py_compile bestellung.py
✓ Check bestanden: python -m pytest -q
Merke: Jeder Schritt bekommt nur die Werkzeuge seiner Phase und eine kurze Zusammenfassung der vorigen Schritte. Danach prüft lcc selbst.
Lektion 4 · Kleinmodell-Modus Fall 3 / 4

Den Plan bearbeiten

Ziel: Den Plan selbst vorgeben, wenn er dir nicht gefällt.

Du tippst
[Enter] ausführen / [e] bearbeiten / [n] abbrechen: e
> explore: bestellung.py und main.py lesen
> edit: Gewicht in lies_formular mit float() umwandeln
>
Du siehst
Plan:
1. [explore] bestellung.py und main.py lesen
2. [edit] Gewicht in lies_formular mit float() umwandeln
[Enter] ausführen / [e] bearbeiten / [n] abbrechen:
Probier auch: Eine Zeile pro Schritt im Format „phase: Ziel“, leere Zeile beendet. n bricht ab, ohne etwas zu ändern.
Lektion 4 · Kleinmodell-Modus Fall 4 / 4

Wenn eine Prüfung rot ist

Ziel: Verstehen, wie lcc repariert – und wann es ehrlich aufgibt.

Du tippst
# lcc prüft nach den Änderungen automatisch:
# py_compile für geänderte Python-Dateien,
# pytest, wenn es tests/ gibt
Du siehst
✗ Check fehlgeschlagen: python -m pytest -q
↻ Repair-Versuch 1: Fehler aus den Checks zurück an das Modell
▶ Schritt 3/3 [edit]: Behebe diesen Fehler: …
✓ Check bestanden: python -m pytest -q
Merke: Bleibt es rot: Abbruch mit Exit 1, letzter Fehlermeldung und Hinweis auf lcc undo – nie „Erfolg“. Prüfe danach: python main.py → Petra Lindner: 7.03 EUR

Ein Skill ist eine kurze Anleitung für genau eine Art von Aufgabe. lcc lädt ihn nur, wenn der Auftrag passt.

Das lernst du

  1. vorhandene Skills ansehen
  2. verstehen, welcher Skill geladen wird

Lektion 7 · Skills Fall 1 / 7

Vorhandene Skills ansehen

Ziel: Wissen, welche Skills im Projekt bereitstehen.

Du tippst
lcc skills
lcc skills show changelog-eintrag
Du siehst
abap-unit-test        Projekt  Legt eine ABAP-Unit-Testklasse an …
changelog-eintrag     Projekt  Ergänzt CHANGELOG.md …
commit-nachricht      Projekt  Formuliert eine Commit-Nachricht …
…
Merke: Das Modell sieht zunächst nur Name und Beschreibung – den Inhalt erst, wenn er passt. Das hält den Kontext klein.
Lektion 7 · Skills Fall 2 / 7

Welcher Skill wird geladen?

Ziel: Vor dem Auftrag prüfen, was lcc wählen würde.

Du tippst
lcc skills match "trag ins Changelog ein: Versand funktioniert jetzt"
Du siehst
changelog-eintrag  1.00  Trigger 'changelog'  wird automatisch geladen
commit-nachricht   0.49  Ähnlichkeit 0.49     im Systemprompt gelistet
Merke: Trigger (Stichwort im Auftrag) → Score 1.0. Sonst zählt die Ähnlichkeit: ab 0.55 wird geladen, darunter nur gelistet.

Lektion 7 · Skills Fall 6 / 7

Eigener Skill (2/3): SKILL.md

Ziel: Beschreibung, Trigger, Werkzeuge und Schritte festlegen.

Du tippst
---
name: todo-sammeln
description: Sammelt alle TODO-Kommentare in TODO.md.
  Nutzen bei "TODOs sammeln", "offene Punkte".
triggers: todo, todos, offene punkte
tools: search_code, read_file, write_file
---
# TODOs sammeln
## Vorgehen
1. Suche mit `search_code` nach `TODO`.
2. Schreibe `TODO.md` mit `write_file`.
## Nicht tun
- Code ändern.
Du siehst
description  → was + wann; sieht das Modell immer
triggers     → sichere Stichwörter
               (Wortgrenzen: todo ≠ todos)
tools        → nur diese, solange aktiv
Vorgehen     → nummerierte Schritte mit Tool-Namen
Nicht tun    → ausdrücklich nennen
Merke: Kurz halten: ideal 1500–3000 Zeichen. Ein kurzes Beispiel am Ende hilft dem Modell mehr als jede Beschreibung.

Ziel: Den Skill testen – und arbeiten lassen.

Du tippst

Du siehst

Lektion 7 · Spickzettel

Faustregeln für gute Skills

  • Ein Skill = eine Aufgabe. Lieber drei kleine als einen großen.
  • Kurz: ideal 1500–3000 Zeichen.
  • Nummerierte Schritte mit klaren Verben und Tool-Namen.
  • Ein kurzes Beispiel schlägt jede Beschreibung.
  • „Nicht tun“ ausdrücklich nennen.
  • Trigger mit Bedacht – zu allgemeine laden ständig.
  • tools einschränken, wenn nichts geändert werden soll.
  • checks nur mit Befehlen aus der Allowlist.

lcc anpassen

Einstellungen fürs Projekt oder für dich – ohne Code zu ändern.

Das lernst du

  1. sehen, welche Einstellung woher kommt
  2. die Allowlist erweitern
  3. Projektregeln für das Modell festlegen
Lektion 8 · lcc anpassen Fall 1 / 3

Woher kommt eine Einstellung?

Ziel: Die wirksame Config mit Herkunft jedes Werts sehen.

Du tippst
lcc config show | less
Du siehst
[ollama]
base_url = "http://192.168.178.79:11434"  # Default
[models]
code = "qwen3.5:9b"  # Default
embed = "bge-m3"  # Default
Merke: Reihenfolge: Defaults → ~/.config/lcc/config.toml → ./.lcc/config.toml → --config → Umgebung → Flags. lcc config init legt die Benutzer-Config an.
Lektion 8 · lcc anpassen Fall 2 / 3

Die Allowlist erweitern

Ziel: python main.py ohne Rückfrage erlauben – nur in diesem Projekt.

Du tippst
cat > .lcc/config.toml <<'EOF'
[agent]
shell_allowlist = ["ls", "cat", "rg", "grep",
  "git status", "git diff", "pytest", "python -m pytest",
  "python -m py_compile", "python main.py"]
EOF
lcc config show | grep shell_allowlist
Du siehst
shell_allowlist = [… "python main.py"]  # …/.lcc/config.toml
Merke: Verglichen wird der Anfang des Befehls: python main.py erlaubt genau diesen Aufruf, nicht python anderes.py.

Mit --json liefert lcc maschinenlesbare Ereignisse – für Skripte und Pipelines.

Lektion 9 · lcc in Skripten Fall 1 / 2

JSON-Ereignisse

Ziel: Eine Antwort maschinenlesbar weiterverarbeiten.

Du tippst
lcc --json ask "Antworte nur mit: ok" | tail -1
lcc --json run --yes "Sammle alle TODOs" \
    | jq -c 'select(.type=="check")'
Du siehst
{"type": "final", "content": "ok", "model": "qwen3.5:9b", …}
{"type": "check", "command": "python -m pytest -q", "ok": true, …}
Merke: Typen: token, tool_call, tool_result, plan, step, check, info, final, error. Ohne Terminal fragt lcc nie – Schreiben nur mit --yes.
Lektion 9 · lcc in Skripten Fall 2 / 2

Hat es geklappt?

Ziel: Den Exit-Code im Skript auswerten.

Du tippst
lcc run --yes "…"; echo "exit=$?"
Du siehst
exit=0     ok
exit=1     nicht erfolgreich (z. B. Checks rot)
exit=2     Config-Fehler
exit=3     Server nicht erreichbar
exit=4     Modell fehlt
exit=130   Abbruch mit Strg-C
Merke: Bei exit=1 nach Änderungen: git diff ansehen, ggf. lcc undo.
